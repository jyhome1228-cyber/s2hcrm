# S2H CRM UI 운영 기준 (2026-11-24)

## 방향
플로우·잔디 등 국내 업무 SaaS의 사용성을 참고하되 디자인을 복제하지 않는다. S2H 고유 로고와 브랜드 블루를 유지한다. 화이트 배경에 명확한 정보 구조, 가독성 높은 목록, 줄 단위 작업을 기본으로 한다.

## 컬러
- Primary: `#0089B3` / hover `#006F94`
- Background: `#FFFFFF`
- Text: `#22292E`
- Secondary text: `#556269`
- Muted text: `#718087`
- Divider: `#DFE5E8`
- Hover: `#F3F8FA`
- 상태 색상은 불필요하게 여러 색을 쓰지 않는다. 진행 중은 S2H 블루, 예정은 블루 아웃라인, 완료는 회색 중심.

## 레이아웃 및 타이포그래피
- 사이드바 고정 폭 232px(중간 해상도 208px), 모바일은 가로 스크롤 내비게이션.
- 상단 헤더 64px, 현재 페이지 표시, 실행 가능한 셀러 검색, 사용자·로그아웃.
- 콘텐츠 최대 폭 1560px, 데스크톱 기본 좌우 패딩 40px.
- 서체 Pretendard 우선. 페이지 제목 26px, 패널 제목 17px, 본문 13–14px, 보조 12px.
- 둥근 카드를 반복하지 않는다. 2–4px 라운딩, 얇은 구분선, 최소한의 그림자.
- 기본 버튼 높이 40px, 미니 버튼 약 31px, 표 셀 높이는 행 패딩으로 정렬.
- 포커스, hover, disabled, 로딩, 빈 상태를 생략하지 않는다.

## 공통 컴포넌트
- `ui-system.css`: 인증 후 앱 셸, 공통 버튼·테이블·인풋·기본 모달.
- `dashboard-v4.css`: 대시보드와 기간형 공구 캘린더. 날짜·막대 그리드 높이 유지.
- `buy-editor.css`: 공구 등록·수정 전용. 기본 정보, 운영 정보, 추가 정보.
- `styles.css`: 기존 앱 기능·기반 스타일. 새 CSS는 이 파일을 대체하지 않는다.

## 동작 원칙
- 기존 Firebase 스키마와 셀러·상품·공구·활동 내역을 변경하지 않는다.
- 사이드바 페이지 이동, 셀러 검색, 공구 등록·수정, 선택한 날짜 등록, 캘린더 기간 표시·더보기는 동작해야 한다.
- 현 점검 모드(`MAINTENANCE_MODE`)는 최종 검수 전까지 유지한다.
- 기능 검수 전에는 "운영 전환 완료"를 표시하지 않는다.

## 단계별 작업
- **STEP 1** 공통 UI 시스템: 셸/내비게이션/타이포그래피/버튼/테이블/모달 통일
- **STEP 2** 핵심 업무 화면: 대시보드/캘린더/셀러/상품/활동 정보 위계 및 인터랙션 고도화
- **STEP 3** 오픈 준비 체크리스트, 담당자·알림·이력, Firebase 권한과 전체 QA 후 점검 종료


## STEP 2 구현 결과 (2026-11-24)
- 대시보드: 오늘 처리할 업무를 전체·오늘 오픈·연락 필요로 전환하여 확인.
- 공구 일정: 간편 목록·상세 대장·기간형 캘린더 전환, 상태별 필터, 셀러/상품 검색, 목록 정렬. 상세 대장은 수평 스크롤 유지.
- 셀러 관리: 전체·진행 중·오픈 예정·연락 필요·공구 이력 없음 필터. CSV는 현재 검색·운영 상태 필터 결과만 내보냄.
- 상품 관리: 브랜드 이름·공구 이력·진행 셀러 수·최근 공구 기준 정렬.
- 활동 기록: 내용/담당자/셀러 검색, 활동 유형 선택, 35건 단위 페이지 이동.
- 기존 기간형 월간/주간 캘린더의 막대와 더보기, 날짜 클릭 등록, 상세 수정 유지.
- Firestore 컬렉션이나 사용자 데이터 변경 없음. 점검 안내 화면 및 관리자 우회 로그인 유지.
- 신규 표시 스타일: `phase2-workspace.css`로 분리하여 기존 `ui-system.css` 위에 적용.

### 검수 진행
- JavaScript 구문 검사 및 데이터 샘플 기반 공구 상태·셀러 필터·상품 정렬·활동 기록 분류 테스트 확인.
- 최종 브라우저 화면, Firebase 실계정 로그인 및 모바일 UI 점검은 별도 필요.
- 운영 재개 전 Firestore Security Rules 점검도 필요. 현재 점검 모드는 기본적으로 UI 접근 제한이며 보안 규칙 자체를 바꾸지 않았음.

## STEP 3 구현 및 운영 검수 (2026-11-24)

### 반영 내용
- 공구별 `readiness` 필드를 신규 사용. 기존 `sellers`·`products`·`groupbuys`·`activities` 컬렉션과 원본 공구 필드는 유지.
- 준비 확인 5항목: 공구 구성표 전달, 홍보 콘텐츠 전달, 결제 링크 전달, 공구 조건 최종 확인, 실제 오픈 확인.
- 담당자 지정: 활성 사용자 `users` 목록에서 선택. 담당자 정보와 단계별 확인자·확인 시각 저장.
- 오픈 전 4개 준비 항목을 점검하며 실제 오픈 확인은 오픈일 이전 체크 불가.
- 대시보드에 오픈 전 D-3부터 오픈 후 2일까지 준비 미확인 대상 노출. 기존 이력이 없는 데이터는 '확인 기록 없음'으로 표시.
- 준비 체크 저장 시 Firebase `writeBatch`로 `groupbuys/{id}.readiness` 갱신과 `activities` 활동기록 생성 묶음 처리. 상태 변경이 없으면 중복 활동 로그 생성하지 않음.
- 공구 일정의 간편 목록과 공구 수정창에서 준비 체크 열기. 활동기록과 전체 데이터 백업에서 이력 확인 가능.
- UI는 화이트/블루 `phase3-preflight.css`를 추가하여 기존 SaaS 디자인과 통일.
- 일정 기준 알림은 CRM에 접속했을 때 표시하는 인앱 알림임. 카카오톡·이메일·푸시로 자동 발송되지 않음.

### 데이터 규칙
- `readiness.ownerUid`, `ownerName`, `paymentUrl`, `memo`, `checks`, `updatedAt`, `updatedByUid`, `updatedByName`.
- `checks.{composition,creative,payment,terms,opening}`에는 `done`, `actorUid`, `actorName`, `at` 저장.
- `activities/{id}`에 `groupbuyId`, `sellerId`, `sellerName`, `type: 공구 준비 확인`, `memo`, `actorUid`, `actorName`, `contactOwner`, `createdAt` 기록.
- 원본 데이터에 체크 기록이 없다면 미완료로 단정하지 말고 미확인으로 표시한다.

- [ ] 실사용 검수 완료 후 점검 모드 종료

**점검 모드 `MAINTENANCE_MODE=true`는 검수 완료 전까지 유지.**

### 임시 서버 접근 제한 규칙 준비
- `firestore.maintenance.rules`는 관리자인지 확인하는 **별도 검토용 파일**임.
- 이 파일을 GitHub에 추가하는 것만으로는 Firebase 서버 규칙이 변경되지 않음.
- 점검 기간에 실질적인 DB 접근 제한이 필요한 경우 Firebase Console에서 보안 검토 후 별도로 게시해야 함.
- 운영 재개 시에는 일반 직원용 규칙으로 신중히 복구해야 하며, 이전 `firestore.rules` 파일의 적합성을 다시 검토할 것.
- 이 대화에서는 Firebase Console 게시나 실제 관리자 계정 로그인 테스트를 수행하지 않았음.

### 추가 단위 검수
- D-3, D-1, 오픈 당일, 오픈 후 2일, 취소 및 이전 데이터 미기록 판정 11개 샘플 확인.
- 공구 수정과 준비 확인 진입 경로, 담당자 선택, 새 체크값 유지, 원본 공구 필드 보존, 원자적 활동 로그, 변경 없음 저장 시 중복 로그 미생성 시뮬레이션.
- 오픈 이전의 '실제 오픈 확인' 체크 입력은 비활성화되어 있으며 저장 로직에서도 차단됨.
- 기존 공구와 활동 이력은 보존되고 새 `readiness` 필드만 추가되는 구조임.
